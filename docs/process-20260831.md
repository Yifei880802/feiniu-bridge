# 过程记录 2026-08-31：MCP 隧道反复断连的根因排查与 /sag-mcp/ HTTP 自愈代理（v1.1.1）

> 本文件已脱敏：域名、IP、令牌均为占位示例（`remote.example.com` / `192.168.1.100` / `k7m9x2p_REPLACE_ME`），不是真实值。

## 背景

知识库 MCP 服务器以 stdio 方式接入 Agent 桌面端，底层是一条常驻隧道：

```
Agent 桌面端 ── stdio ──▶ ssh ──ProxyCommand──▶ websocat ──wss──▶ 公网边缘 ──▶ 本网关 /ssh-ws ──▶ sshd ──▶ docker exec 知识库 MCP 进程
```

该连接在 2026-08-27 ～ 08-28 间三次断开，每次断开后 Agent 端连接器停留在 failed 状态（stdio 子进程退出后不会自动拉起），只能手动禁用→启用恢复。

## 根因排查

三次断连的客户端日志签名完全一致：`WebSocketError: I/O failure` → `closed by remote host` → `Broken pipe`。逐一与隧道侧证据比对：

| # | 时间 | 隧道侧证据 | 判定 |
| --- | --- | --- | --- |
| 1 | 08-27 | 隧道日志该时间窗无任何异常 | 客户端侧网络事件（切网/休眠唤醒） |
| 2 | 08-28 上午 | 隧道日志该时间窗无任何异常 | 客户端侧网络事件 |
| 3 | 08-28 傍晚 | 隧道 "connection with edge closed"，重注册耗时约 4 分钟 | NAS 侧外网整段抖断，在途 WS 全灭 |

另查证：隧道客户端进程（fnOS 应用形态）在 08-29 夜间自身重启过一次——任何一次这类重启同样会杀死所有在途长连接。

**结论**：断连不是空闲超时（曾加 SSH keepalive 30s，仍在 25 分钟后断），而是任一侧真实网络抖动。长连接 WS + stdio 的组合天生脆弱，keepalive 防不了断网。

## 方案权衡

- **A. 维持 stdio + 手动重连**：零改动，但问题反复出现。
- **B. 换 HTTP 传输（采纳）**：知识库服务自带标准 Streamable HTTP MCP 端点（`/mcp/`，带 JWT 认证）。HTTP 无状态——每次工具调用是独立请求，网络恢复后下次调用自动成功，无需人工干预。
- 包装脚本自动重启 ssh 不可行：stdio 上层是 MCP 协议，重启底层进程无法恢复已完成的 initialize 握手。

## v1.1.1 变更内容

新增 `/sag-mcp/{subpath}` 代理路由（GET/POST/DELETE）：

- 鉴权：`X-SAG-Token` 头或 `?token=` 查询参数，`hmac.compare_digest` 时序安全比较；未配置令牌时返回 503 禁用
- 上游认证由网关代持：以单用户身份登录知识库 API 取 JWT，内存缓存，上游 401 时自动重登重试一次
- 流式转发（httpx `stream=True` + `StreamingResponse`），透传 `Mcp-Session-Id` 等会话头，剥离 hop-by-hop 头与客户端 Authorization
- 日志只记方法/路径/状态码；uvicorn 关闭 access log，避免令牌出现在请求行日志
- Dockerfile 增加 httpx 依赖；compose 增加 `SAG_MCP_TOKEN` 环境变量

## 部署纪要（非常规路径）

`docker compose build` 需拉取基础镜像，当时家宽下行仅约 5KB/s，不可接受。改用：

1. 运行中容器内 `pip install httpx`（走国内 PyPI 镜像，数百 KB）
2. `docker cp` 新 gateway.py 进容器
3. `docker commit`（`--change` 更新 CMD 加 `--no-access-log`）覆盖原镜像标签
4. `docker compose up -d`（不带 --build）重建容器注入 `SAG_MCP_TOKEN`

注意：commit 路径使镜像与 Dockerfile 构建产物等价但历史不同；在干净环境部署仍应走 `docker compose build`。
