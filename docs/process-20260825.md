# 过程文档：SSH 公网打通与网关演进（2026-08-25）

> 本文已脱敏：域名（`*.example.com`）、IP（`192.168.1.100`）、主机名等均为占位示例，不是真实值。

## 背景

fnOS NAS（ME mini，192.168.1.100）此前的远程操作全靠 trim-cli（fnOS WebSocket 结构化接口），没有通用 shell。用户已在 fnOS 开启 SSH 并做过公网映射，但办公室始终连不上，需要排查并真正打通。

## 排查过程

1. **局域网直连失败**：办公室 Mac 到 192.168.1.100:22 超时——不在同一局域网，符合预期。
2. **ssh.example.com 无效**：用户记忆的映射域名（占位示例），22 及常见替代端口（2222/22222/5622/8022/22022/2200）全部超时。
3. **找到真实映射 remote.example.com**：用户截图显示 fnOS 面板里映射 Service 为 `http://192.168.1.100:22`。实测：
   - `curl https://remote.example.com/` → 403（网关把 HTTP 请求发给 sshd，解析不了响应）
   - `ssh -p 443` → Connection reset（TLS 边缘收到 SSH 握手直接重置）
   - 结论：**公网边缘是 fnOS 内置 L7 反代，只懂 HTTP/WS，无 TCP 透传**，把 SSH 端口配进去永远不通。
4. **确认边缘身份**：一度怀疑自研容器 fnos-gateway 是边缘，dump 其源码（1276 字节）后发现它只是个 HTTP→fnOS ws 的 appcgi 桥（v1.0.0，2026-08-17 建），真正的边缘是 fnOS 系统自带的反代面板。关键旁证：QwenPaw 控制台的 WebSocket 能穿过公网 → 边缘支持 WS 升级。

## 方案选型

- TCP 透传：fnOS 反代不支持，排除。
- 独立 websockify 容器：可行但需拉新镜像、多一个常驻组件。
- **改自研 gateway.py 加 WS→22 桥接**（选定）：容器里已装 `websockets` 库，加约 30 行；复用现有容器与映射，零新增组件。

## 实施

1. gateway.py v1.1.0：新增 `@app.websocket("/ssh-ws")`，accept 后 `asyncio.open_connection(192.168.1.100, 22)`，双向 pipe（WS 收 bytes/text→TCP，TCP read→WS send_bytes），任一端断开即收尾。原件备份 `gateway.py.bak-20260825`。
2. 镜像是 build 时 COPY 代码，所以 `docker cp` 新文件进容器 + `docker restart` 生效（根路径返回 v1.1.0 确认）。
3. NAS 内自测：容器内 python websockets 客户端连 `ws://192.168.1.100:8081/ssh-ws` 拿到 `SSH-2.0-OpenSSH_9.2p1` banner。
4. 用户在 fnOS 面板把 remote.example.com 的 Service 改指 `http://192.168.1.100:8081`。
5. 客户端：`brew install websocat`；`~/.ssh/config` 加 Host nas（ProxyCommand websocat -b wss://.../ssh-ws，原配置备份 .bak-20260825）。
6. 端到端验证：`ssh nas` 成功（hostname 略）。
7. 加固：推 ed25519 公钥 → 验证免密 → `/etc/ssh/sshd_config.d/trim_sshd.conf` 追加 PasswordAuthentication/KbdInteractiveAuthentication no → `systemctl reload ssh` → 验证密码方式被拒（`Permission denied (publickey)`）、密钥仍可用。

## 踩过的坑

- **expect 报 "The system has no more ptys"**：本机 pty 偶发耗尽，非交互输密码改用 `SSH_ASKPASS=<脚本> SSH_ASKPASS_REQUIRE=force DISPLAY=:0`。
- **`docker exec` 传 heredoc 静默无输出**：必须加 `-i`，否则 stdin 不转发，python 读 EOF 直接退出 0。
- **sudo 无 tty**：`echo pwd | sudo -S`。
- **镜像 COPY 代码**：只改挂载目录/部署目录不 docker cp，restart 无效、重建回退旧版——deploy.sh 里固化了正确流程。
- trim-cli session 过期（wss 失败/errno 135168）：重新 login 即可（本轮早期仍用 trim-cli 时遇到两次）。

## 遗留与注意

- 若重建 fnos-gateway 容器，先 `docker compose build` 把 v1.1.0 烤进镜像，否则 /ssh-ws 消失。
- fnOS 的 SSH 开关若被面板重写 trim_sshd.conf，加固行可能丢失，需复查。
- /ssh-ws 无自身认证，安全边界在 sshd 密钥；如需收紧加 query token。

## Agent 直调能力验证与遗留（同日补记）

网关天然是 Agent 直调通道——08-25 这次 SSH 打通的排查与修改全程由 Agent（QoderWork）经本网关自主执行，验证了 Agent 可像人一样操作 NAS。直调分两层：

- **`/ssh-ws`（已验证，主通道）**：Agent 经 websocat 拿完整 shell，shell/scp/sudo 全可用。配套 fnos-remote-ops 技能（归档于 `../skill/`）固化了通道选择与变更流程。
- **`POST /api/{endpoint}`（待通，v1.2）**：结构化 HTTP 面（同 trim-cli 协议）本更适合程序化调用，但 fnOS ws 有登录墙——裸 ws 连接上所有请求（`appcgi.dockermgr.containerList`、`appcgi.usersrv.login`、`user.authToken`、`user.tokenLogin` 明文与 token 变体均试过）一律返回 errno 65534。从 trim-cli 二进制 strings 确认官方登录流为 `user.authToken` → `user.tokenLogin` 两段（字段 token/longToken/backId/secret），握手尚未复现。v1.2 目标：实现两段握手或注入已登录 session。

结论：握手打通前，Agent 直调一律走 `/ssh-ws`；`/api` 不可用是已知事实，不虚构能力。
